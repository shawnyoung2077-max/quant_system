# 静默死亡 36 小时：代理掉线 + 失败无回执

日期：2026-10-12
影响：**系统从 10-10 20:45 到 10-12 10:20 完全停摆，约 36 小时零产出。**
发现方式：**用户问"polymarket 怎么样了"才发现的。** 这是本会话第 4 次静默失败。

---

## 1. 症状

```
任务状态    : Running（看着一切正常）
LastResult  : 2147946720       ← 非 0，但没人会去看
runs 表最新 : 2026-10-11T02:06  ← 32 小时前
日志目录    : 一直在写，但每一份都只有 "[1/4] 扫描 Polymarket ..."
```

`digest_latest.txt` 和 `report_latest.txt` 也一起停在 10-10。

## 2. 根因链

**(a) 代理没在跑。** `_detect_proxy()` 返回 `None`，7897/7890 都没监听，连 Google 都连不上。

Clash Verge 是 **GUI 程序**：服务 `clash_verge_service` 只负责 TUN/提权辅助，
**内核 `verge-mihomo` 是由 GUI 拉起来的**。所以它没启动时，代理就不存在。

机器在 10-12 10:01 重启过，但那只是最近的事 —— **故障在重启前 36 小时就开始了**。

**(b) 473 个 tag 全部请求失败**，`累计 0 个市场`，133 个 tag 明确报 API 错误。

**(c) 代码在空表上崩了。** `to_frame([])` 得到的 DataFrame 没有 `days_to_start` 列：

```
KeyError: 'days_to_start'
  at scan.py line 465: cand = bet_cand[bet_cand["days_to_start"].notna() ...
```

**(d) —— 这一条才是致命的 —— 崩在第 1 步，第 4 步永远不执行。**

`run.py` 的顺序是 `scan → refodds → settle → report`。
报告和看门狗都在第 4 步。第 1 步抛异常 → 第 4 步跳过 →
**`digest_latest.txt` 不更新 → 看门狗从未运行 → 没有任何告警。**

于是"失败"和"一切正常但还没到时间"看起来完全一样。

## 3. 四个修复

### (a) 网络预检，快速失败 —— `scan.py`

```python
_probe = _get(C.GAMMA + "/markets", {"limit": 1, "closed": "false"}, tries=2, timeout=15)
if not isinstance(_probe, list):
    raise RuntimeError("Polymarket 不可达…当前 PROXY=%s…Clash Verge 没启动是已知原因")
```

旧代码会**傻等满 720 秒墙钟预算**，再抛一个看不懂的 `KeyError`。
现在 **2.8 秒**就报出明确原因（已实测）。

### (b) 抓取 0 个市场 = 抛错，不是返回空表 —— `scan.py`

空表会让下游在 `days_to_start` 上抛 `KeyError`，
**把真实原因（网络坏了）掩盖成一个 pandas 报错**。

### (c) 失败也必须有回执 —— `run.py`

异常分支里现在**照样跑看门狗、写简报**，并把 traceback 摘要追加进
`digest_latest.txt`。打开文件就能看到失败，不需要有人去问。

### (d) 代理自愈 —— `config.ensure_proxy()`

启动时若端口没监听，主动拉起 `clash-verge.exe` 并等内核就绪（最多 45 秒）。
拉不起来也不吞掉 —— 预检 (a) 仍会抛出明确错误。

## 4. 顺带发现：结算在扫描之后，额度要等 2 小时

原顺序 `scan → refodds → settle` 的实际后果：

```
一次结算释放 90 笔、$900 敞口
↓
但**同一次运行里的扫描**看到的仍是结算前的 $1020/$300
↓
全部被风险闸拦下，n_new_bets=0
↓
要再等 2 小时，下一次运行才用得上这笔额度
```

改为 **`settle → scan → refodds → report`**（结算只要 ~10 秒）。
实测改完后同一次运行就下了 **25 笔新注**，且**全部落在过偏差门槛的联赛**
（MLS / 巴甲 / 土超 / 葡超）—— 闸门确认在工作。

## 5. 顺手修一个误报

10-11 那天系统已断，只采到 2533 个市场；10-12 恢复后采到 10812 个。
旧逻辑拿"前一天"直接比，于是报
`观测数从 2533 变到 10812（327%）—— 可能是 API 结构变化或筛选失效`。

**这是误报：异常的是前一天太低，不是今天太高。**
改为与近 7 日中位数比，并对"前一日显著偏低"单独给提示。

## 6. 修复后第一批"证据内"结果

`valid` 线（联赛净偏差 >= 5pp 的 12 个联赛）第一次有了已结算样本：

```
独立市场 23 个（MLS 11 / 墨超 6 / 西乙 4 / 巴甲 2）
平均入场价 0.2526  实际胜率 0.2174
k = -3.52pp   t = -0.40   95%CI [-20.8pp, +13.7pp]
ROI = -20.69%（$230 投入）
```

对照 `explore` 线：

```
独立市场 93 个   k = -2.80pp  t = -0.65  95%CI [-11.2pp, +5.6pp]
```

**两条线都在 −3pp 附近，而且都**在统计上与 0 无法区分**。**
也就是说：历史那个 +20~+33pp 的偏差，在实盘 23 个市场里**没有复现**，
但区间宽到 [−20.8, +13.7]，**既不能确认也不能否定**。

样本量是硬伤 —— 敞口闸门 + 36 小时停摆，两天只攒到 23 个独立市场。

## 7. 教训（第 4 次同类）

前三次是：结算恒为 0、联赛覆盖截断、报告分母不清。
这一次是：**代理掉线 + 崩溃无回执**。共同点完全一样：

> **失败和成功看起来一样。**

具体的防御手段只有一条是通用的：**让失败必须留下痕迹。**
这次的做法是——第 1 步崩了，第 4 步照样写出简报并把 traceback 追上去。
以后再遇到"系统好像没动静"，打开 `polytrade_out/digest_latest.txt` 就有答案，
不需要有人想起来问。
