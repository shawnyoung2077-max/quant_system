## 1. 要回答的问题

策略假设（来自历史研究）：**Polymarket 体育市场在低价格档 [0.15, 0.30) 系统性低估**，
即 YES 的实际胜率高于市场隐含概率 7.5~9.0pp。若为真，每笔应有可观正收益。

**唯一的判定证据是实盘纸面账本**，不是历史回测、也不是短窗口探针。

> ⚠️ 教训来源（同一个错误已经犯过一次）：PandaAI 因子研究里，
> 「3 个月探针」跑出 +16%~+30%，换到「5 年窗口」后只剩 3%~10%，
> 而且净正的 4 个因子全都是 size 代理（长腿收益相关性 0.994）。
> 短窗口的漂亮数字是风格漂移，不是 edge。
> 本项目的历史 +7.5~9.0pp 同样是**另一个时期**的测量，不能当作预期收益。

**⚠️ 两个必须按 side 拆开算的理由**

`AVG(entry_price)` 与 `AVG(outcome_yes)` 直接相减是**类别错误**：
买 NO 时 `entry_price` 是 NO 的价格，而 `outcome_yes` 是 YES 的结果。
我第一版就踩了这个坑，算出「$2 档偏差 +24.11pp」，按 side 拆开其实是 −0.87pp。
方向胜率的口径：YES 用 `outcome_yes`，NO 用 `1 − outcome_yes`。

**盈亏平衡（用实测 p 现算，不引用历史）**

    p = 0.2519（$2 档 YES 实付均价）
    手续费 = 0.05 x (1 − p)          = 0.0374   （占投入）
    价差成本 = 0.0087 / p            = 0.0345   （占投入）
    盈亏平衡所需胜率 = p x 1.0719    = 0.2700
    => 必须比市场隐含概率高 +1.81pp 才不亏

实测偏差是 **−0.87pp**，也就是**还在平衡点下方 2.68pp**。

**但样本量远远不够**：每笔收益率标准差 = 2.07，n = 52，**t = −0.57**。
这个样本连「零」和「+24%」都分不开。

## 3. 判定规则（现在定死，之后不许改）

### 3.1 主指标

**已结算注的每笔收益率均值（stake-weighted）及其 t 值。**

- 只统计 `status='settled'`；
- 主窗口 = **2026-10-15 及之后建的仓**（原因见 3.4 的口径断裂说明）；
- 不剔除任何单笔（不许事后剔除"异常值"）；
- 聚类：同一市场多张票按市场去重，避免 t 值虚高。

次指标：**方向胜率 − 市场隐含概率**（按 side 分别算），与盈亏平衡点 +1.81pp 对比。

### 3.2 检查点与动作

第一个检查点：**主窗口满 300 笔已结算** 或 **满 30 天**（先到为准）。

| 观测 | 判定 | 动作 |
| --- | --- | --- |
| t < −2 | 假设被推翻 | **停止下注**，记录结论；不再投入时间 |
| t > +2 | 假设成立 | 可讨论加码，但**必须先经用户明确批准**（涉及回撤风险） |
| \|t\| < 2 | 证据不足 | 延长到 **1000 笔或 80 天** |

第二个检查点（1000 笔 / 80 天），若仍是 \|t\| < 2：
**结论 = 真实 edge 小于约 6%/笔，不值得继续占用资金与维护成本**，停止。

### 3.3 失败保护

- t 值连续两次检查点都为负 → 无论是否显著，都停止并复盘。
- 回撤打穿本金 15% → 立即停止（当前最大回撤约 −4%~−8%）。

### 3.4 口径断裂（必须遵守，否则数据不可比）

**2026-10-15 起下注候选的来源变了**：从「宽扫抓到什么就筛什么」改成
「只从核心抓取（moneyline 类型 + 14 天窗口 + 按到期临近排序）里筛」。
机会集变了 ⇒ 变更前后的收益序列**不是同一个策略**。

- 主指标只算 10-15 之后的仓；
- 10-15 之前的样本单独作为「旧口径」报告，**不与主指标合并**；
- 同理，任何时候再改 `BET_RULES`、`MIN_EDGE_PCT_OF_STAKE`、白名单联赛集合，
  都**重置主窗口的起点**并在本文件里追加一行记录。

#### 3.4.1 ★ 2026-10-16 自我更正：判据从"改了参数"改成"改了合规集合"

我第一版把「改 STAKE」也列成重置触发条件，那是**错的**。
修正后采用一条更立得住、也更少误伤的判据：

> **只有改动「什么算一笔合规下注」才重置主窗口；
> 改动「一次能吃下多少笔」不重置。**

理由：前者的合规集合本身变了，样本不是同一个东西；后者只是**吞吐/容量**参数 ——
过门槛的市场集合一模一样，变的只是"同一批合规注里这次取几笔"。

按这条判据：

| 参数 | 属于 | 是否重置 | 说明 |
| --- | --- | --- | --- |
| `BET_RULES` 价格档 | 合规集合 | **重置** | 直接改变哪些市场合格 |
| `MIN_EDGE_PCT_OF_STAKE` | 合规集合 | **重置** | 直接改变哪些市场合格 |
| 白名单联赛集合 | 合规集合 | **重置** | 直接改变哪些市场合格 |
| 「每市场只下一笔」协议 | 合规集合 | **重置** | 改变计入方式 |
| `STAKE` | 容量/尺度 | 不重置 | 等额下注下 `pnl/stake` 不变 |
| `MAX_NEW_BETS_PER_RUN` | 吞吐上限 | 不重置 | 见下 |
| `MAX_EXPOSURE_PCT` / `MAX_DAILY_NEW_PCT` | 吞吐上限 | 不重置 | 同属容量 |

**对 `MAX_NEW_BETS_PER_RUN` 25→40 的实测旁证**（不是空口判断）：
提高上限后多出来的注来自**更远期的市场**（核心抓取按 `endDate` 升序取前 N 笔）。
若"更远 = 更差"，那这次改动实际上改变了收益分布，就应当重置。实测：

| `days_to_end` | 笔数 | ROI | 每笔均值 | t |
| --- | --- | --- | --- | --- |
| <1 天 | 168 | −17.18% | −19.1% | −1.35 |
| 1–3 天 | 73 | −10.56% | −14.5% | −0.72 |
| >7 天 | 12 | −103.94% | −104.3% | 退化，勿引用 |

- `corr(days_to_end, 每笔收益率) = −0.074`（几乎无关）；
- 分桶均值差 −4.6pp，标准误约 0.29 ⇒ **0.16σ，测不出差异**；
- ⚠️ `>7 天` 那档 ROI −104%、t 值 −711：**那个 t 是退化统计量**
  （12 笔全亏、收益率方差趋零，t 就会爆），**不能当证据**；
  但"12 笔全亏"本身是个黄色信号，样本太小，只能盯着。
- ⇒ 结论：**测不出差异 ⇒ 不重置**，但把下面 4 条列为必看指标。

**改完必须盯着这 4 条**（跑 3~5 轮后核对，不许只看"感觉变快了"）：

1. `runs.n_new_bets` 是否从「3/12 顶到 25」变成「经常接近 40」；
2. **每日新建笔数是否真的从 38~55 升上去 —— 没升就说明判断错了，回退**；
3. 新注的 `days_to_end` 分布与旧注是否明显不同；
4. 新注的每笔收益率是否显著低于旧注（若是，说明远期档真的更差，要回退并重估）。

**保留下来的重置触发条件**：上面表里标"重置"的那四项。

## 4. 当前最卡脖子的事：样本积累速度

**★ 2026-10-16 更正**：我此前写「瓶颈已经从没机会变成等结算」——
按完整数据看**只对了一半**。四道闸的实际占用：

| 闸 | 上限 | 实际占用 |
| --- | --- | --- |
| 每次扫描新建 | 25 笔 | **12 次运行里有 3 次顶到 25**，其余 0~3 笔 |
| 每日新增 | $150（$2 时=75 笔） | 10-12:48 / 10-13:38 / 10-14:55 / 10-15:44 ⇒ **51%~73%** |
| 同时在场 | $300（$2 时=150 笔） | 90 笔 / $220 ⇒ **60% / 73%** |
| 单簇 | $60 | 未报过触发 |

⇒ 真正在削峰的是**「每次扫描 25 笔」**（条件好的运行会被它切掉），
敞口闸还没完全卡死。所以**直接提高敞口上限大概率看不到效果**。

**要提速的正确顺序**：

```
先改 MAX_NEW_BETS_PER_RUN 25 -> 40
   ↓  每日新增向 75 笔/天靠拢
   ↓  75 笔/天 x 1.95 天持仓 ≈ 146 笔 ≈ $292 -> 这才顶到 $300 敞口闸
再改 MAX_EXPOSURE_PCT 10% -> 20%
```

⚠️ 注意上面那条新约束：每天新建笔数一旦超过 75 笔，就构成口径断裂、主窗口要重置。

### ★ 2026-10-16 更正：我对提速幅度的外推错了近一倍

我最初写「约 3~4 次运行/天会出注 ⇒ 上限提到 40 后可达 120~160 笔/天」。
**实测打脸**：全部 61 轮扫描（跨 7.01 天）的 `n_new_bets` 分布是

```
[25,25,25,25,0,0,0,...]   ← 双峰：绝大多数轮是 0，只有 11/61 轮顶到 25
```

平均只有 **1.6 轮/天**顶到上限（不是 3~4）。修正后：

| | 我原来写的 | 实测/修正后 |
| --- | --- | --- |
| 每天顶到上限的运行 | 3~4 轮 | **1.6 轮** |
| 预计日均新建 | 120~160 笔 | **约 70 笔** |
| 攒满 300 笔已结算 | 2.5 天 | **4.3 天** |
| 在场笔数 / 日标准差 | 234~312 笔 / 0.76% | 约 137 笔 / **0.58%** |

**教训**：我把「运行次数」当成了「出注次数」。分布是双峰的，
用均值 × 次数去外推会严重高估。这正是 `check_throughput.py` 存在的意义 ——
它跑出来的第一件事就是纠正我自己写进提交里的数字。

**下一次核对能回答一个更重要的问题**：到底是谁在卡？
- 若运行开始**频繁顶到 40** ⇒ 候选还富余，可以继续提；
- 若停在 **25~40 之间** ⇒ **候选数量**才是真约束，再提无益，该去扩大候选池了。

**关于单注降到 $1 的效果（2026-10-16）**：
- 它**不会自动让样本变快** —— 笔数由候选数量 + 每次上限决定，金额闸只是上限
  （现在只用到 51%~73%，没卡住）。
- 它**确实降低波动**：日标准差 ∝ √stake，减半后降到约 71%
  （$36/1.21% → $26/0.86%），因为在同一敞口下能装下双倍笔数。
- 它把「在手笔数上限」从 150 提到 300（正好等于 `MAX_OPEN_BETS`），
  移除了一个未来的天花板。

| 方案 | 效果 | 代价 |
| --- | --- | --- |
| 提高 `MAX_NEW_BETS_PER_RUN` | **真正能提速**（放松被顶死的那道闸） | 无风险代价，只是下注更集中 |
| 提高 `MAX_EXPOSURE_PCT` | 在手笔数上限变高 | 日波动随敞口线性上升 |
| `STAKE` 降到 $1 | **笔数不变**，但日波动 1.21%→0.86%，在手上限 150→300 笔 | 真实盘口最小 5 股时可能挂不出去（见 config 注释） |
