## 3. 复核中发现、由 DeepSeek 补掉的（本次提交）

### 3.1 核心抓取「静默变空」会让系统一切正常地停止下注 ★最严重

实测 gamma 的行为：

```
sports_market_types=moneyline -> n=20（正常）
sports_market_types=zzz       -> n=0   （不是报错，是空列表）
zzzparam=1（未知参数名）       -> 与不传一样（被静默忽略）
```

而 `fetch_core` 把「空列表」与「正常抓到底」返回成同一个 `issue=None`，
于是 `FETCH_CORE_COMPLETE` 照样为 `True`、简报一切正常 —— **但永远没有下注候选**。

补法：新增 `C.CORE_MIN_CANDIDATES`（默认 20，故意定得很低以免假警报），
核心候选低于阈值时记 `core_empty` 并**禁止本轮下注**。
理由：只剩几个候选还照常下注，等于在一个**有偏的小子集**上下注，比不下注更糟。

> 这个阈值只用来抓「整块塌掉」的灾难，**不是覆盖率达标线**。
> 正常一天核心候选是几百到上千个。

### 3.2 简报告警分级（恢复了被删掉的理由）

上一版把 note 里任何内容都判成 `[警告]`。但 `page_cap`（实测每轮 50+ 联赛打满）
和 `broad_snapshot_partial` 是**每轮必然出现**的 ⇒ 简报每轮报警。
被删掉的那段原注释恰好就在警告这件事：**「告警变成噪音、人开始无视它，
而那正是静默少采能藏两天的土壤」**。

现在的分级（原则：**只有「决策样本本身不可信」才是严重**）：

| 等级 | 触发 | 含义 |
| --- | --- | --- |
| 严重 | `core_incomplete` / `core_empty` | 下注候选抓取残缺，本轮的「没下注」不能当策略信号读 |
| 警告 | `core_api_errors` | 核心抓取遇 API 错误（可能偶发） |
| 提示 | `page_cap` / `broad_snapshot_partial` / `time_budget` | 只影响宽口径观测完整度，不影响下注决策 |

### 3.3 把三条 API 硬约束写进 `config.py`

因为它们是**静默的隐式耦合**，后人一「简化」就会炸：

1. `child_moneyline` / `first_half_moneyline` 作为过滤值实测 **n=0**，是**死值**
   （字段可能出现该取值，但不是合法的过滤取值）。
   历史上有 6 笔注的 market_type 是 `child_moneyline`（$12）——
   这些市场以后不会再被抓到、也就不会再下注。
2. `end_date_min/max` **单独使用会 HTTP 500**；只有与 `sports_market_types`
   同时传才正常。所以 `fetch_core` 里那两行不是冗余，**删不得**。
3. **未知参数名会被静默忽略** ⇒ 任何新加的过滤参数都必须用真实 API 验证
   它**确实改变了返回集**，不能「加上了就以为生效了」。

## 4. 实测验证结果（2026-10-15，两轮对照）

**这是 Codex 那套改动的第一次真实全量验证，结论：改动本身是对的，但需要下面这两处修正配合。**

| 指标 | 12:05 那轮（Codex 版，未修正） | 14:05 那轮（修正后） |
| --- | --- | --- |
| `scanned` | **1,578** | **89,931**（57 倍） |
| `core_complete` | **False** | **True** |
| `core_candidates` | 接近 0 | **6,698** |
| `bet_candidates` | 0 | **1,991** |
| `n_bets` | **0** | **25** |
| AI 预测 | `asked=21, stored=0, failed=21` | `asked=25, stored=25, failed=0` |
| 整轮耗时 | 883s（但没做事） | 1,179s（预算 1,560s） |
| 简报问题 | `[严重] core_incomplete` + `[提示]` | **两条 `[提示]`**（page_cap / broad_snapshot_partial） |
| 参照价与 AI | 都被预算跳过 / AI 全失败 | **两步都正常执行** |

**12:05 那轮到底发生了什么（我纠正了自己两次错误猜测）**

- 猜测一：「`tries=1` 太激进导致限流」→ **被实验否定**。
  150 tags × 8 并发，`tries=1/timeout=10` 连跑两遍 0 失败；
  完整 473 tags 连跑 3 遍（1,419 次请求）**只失败 1 次**。
- 猜测二：「撞上我正在编辑 `scan.py`」→ **被时间戳否定**。
  `ab3b176` 提交于 13:43:19、文件 mtime 13:43–13:47，而运行发生在 12:05–12:20。
- 结论：**一次外部瞬时中断**（Clash 日志 12 点无任何事件 = 代理没重启；
  同轮 `settle` 成功结算 27 笔 = 运行开始时网络是通的）。

**但它暴露了两个真问题，已修：**

1. **单次坏轮完全不可见**：`observations` 按 `(market_id, snap_date)` 去重，
   一天多次运行会合并成一行 ⇒ 按天统计看不到单次坏轮
   （12:05 只采到 977 个，当天计数仍是 ~15,000）。
   已新增按【单次运行】的采集量检查（用 `runs.n_new_obs`）。
   实测：峰值 14,903 → 977 现在会明确报警「该轮观测不应当作完整快照使用」。
2. **重试韧性被归零**：`tries=1` 一次抖动就毫无还手之力，
   而本仓库早就实测过这条链路会抖。已改 `FETCH_HTTP_TRIES=2 /
   FETCH_HTTP_TIMEOUT=15`（最坏单请求 30 秒，仍然有界）。

## 6. `run_match` 索引化（DeepSeek，2026-10-15）

**问题**：实测 14:05 那轮 —— `6087 市场 x 79 赛程 = 480,873 次比较`，
`进度 1000/6087 用 139s` ⇒ 全量约 845s，而该步预算 **417s** ⇒
**必然被截断，匹配覆盖率实际只有约一半**。

**根因**：原实现每个市场都在重复做三件与市场无关的昂贵事 ——
`pd.to_datetime(commence_time)`（48 万次日期解析）、
`_tokens(home/away)`（正则+建集合）、以及遍历**全部** 79 条赛程
（而 `max_day_gap` 只有 2 天，绝大多数根本对不上）。

**修法**：`prepare_fixture_index()` 预计算时刻与队名 token 并按**日期分桶**，
每个市场只看 `end_date` 前后 `ceil(gap)+1` 天的桶。分桶取**超集**，
精确判定仍走原来的 `gap` 逻辑 ⇒ 语义零变化。

**实测（真实数据，非微基准）**：

| 指标 | 结果 |
| --- | --- |
| 等价性（4000 个市场逐条对比旧实现） | **0 处差异**，匹配数 113 = 113 |
| 纯匹配速度 | 586.7s → 5.3s（**110.7×**） |
| 生产步骤（6087 个市场） | 417s 后被截断 → **11 秒跑完** |
| 匹配数 | 114 → **122**（覆盖变全，多找到 8 个） |
| 释放的预算 | 约 400s，可给其它步骤 |

**回归测试** `TestMatchIndexEquivalence`（6 条）含一条**性能回归**：
1001 条赛程里 token 比较次数必须 < 50 —— 谁把索引去掉退回全表扫描，立刻失败。
