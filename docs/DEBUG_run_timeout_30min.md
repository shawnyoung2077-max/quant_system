# 事故：整轮运行撞上计划任务的 30 分钟硬上限被强杀

日期 2026-10-14。发现过程：为了验证另一个修复，手动触发了一次运行，
结果在 `cron.log` 里看到它跑到 10:24 就没了下文。

---

## 1. 为什么这件事很严重

被硬杀 = 进程直接消失，没有机会写任何东西。而报告、看门狗、简报都在**最后一步**。
于是：

- `report_latest.txt` / `digest_latest.txt` 一起停在旧版本；
- 没有任何错误信息 —— 从外面看，系统只是"没什么新东西"；
- 这与仓库里已经记录过的第 5 条 bug（**崩溃无回执**）是同一个形状，
  只是这次的触发者从"抛异常"变成了"超时"。

所以这条的严重性和"代理静默死 36 小时"是同一级别。

**而且 ExecutionTimeLimit 改不了。** `Set-ScheduledTask` 需要账户密码：

```
The user name or password is incorrect
```

本机不是管理员，也没有该账户的密码。⇒ 只能让运行去适应 30 分钟这个天花板。

---

## 2. 第一次修复（不完整）

给整轮运行加墙钟预算 `RUN_BUDGET_SEC`，每步开跑前检查剩余时间，
不够就跳过并明确上报；报告与看门狗永远执行（`RUN_RESERVE_SEC` 保留额）。

**小预算演练证明了它有效**：

```
POLYTRADE_RUN_BUDGET_SEC=120 python -m polytrade.run --dry
  [2/5] 本轮剩余预算 104s -> 抓取预算 60s
        ⚠ 预算不足，跳过 参照价+匹配赛程：剩余 -3s，需要 180s + 保留 240s
        ⚠ 预算不足，跳过 AI 赛前预测：剩余 -3s，需要 90s + 保留 240s
  [5/5] 报告已写出 / 简报已写出          ← 关键：预算耗尽也照样留痕
```

**但它没能防住真实场景。** 11:06 那次完整运行的实际数据：

```
[2/5] 本轮剩余预算 1541s -> 抓取预算 720s     {'scanned': 83321, ...}
[4/5] 参照价预算 655s（剩余 895s）
      赛程 0 条 / 匹配 114 个市场 / 填入 ref_fair 114 行
      ⚠ 预算不足，跳过 AI 赛前预测：剩余 -205s
      整轮耗时 1765s（预算 1560s，保留 180s）
[5/5] 报告 + 简报 均正常写出
```

两点：

1. 整轮 **1765s**，离 PT30M(1800s) 只剩 **36 秒** —— 这次是侥幸没被杀；
2. 参照价那一步拿到 655s 预算，**实际跑了 1100s**。

⇒ 结论：**只给"整轮预算"是不够的。**
某一步内部如果是个长循环，它读不到整轮预算，整轮预算就形同虚设。

## 3. 真凶：`match.run_match` 的无上限 O(N×M) 循环

`cron.log` 里有 **17 分钟完全没有任何输出**（10:47:46 → 11:05）。
这不是"慢"，而是**看起来像卡死**。定位到：

```python
for _, r in ms.iterrows():                     # N 个市场（近期胜负类，上万个）
    m = match_market(..., fixtures)             # 内部再遍历 M 条赛程
```

`match_market` 内部对 `fixtures` 逐条比较 ⇒ 总代价 **N × M 次纯 Python 比较**，
之前**一句日志都不打**，也**没有任何上限**。

我最初把责任归给了 refodds 的网络请求（"几十个联赛 × 5 次重试 × 40s 超时"），
**这个判断是错的** —— 日志里 refodds 大部分联赛都因 24 小时缓存直接跳过，
根本没发几次请求。真正的耗时全在它后面的匹配循环里。

> 教训：**"没有输出"不等于"在等网络"。** 定位慢步骤要靠日志里的实际耗时，
> 而不是靠对代码的想象。我这次就是先想象了原因、还照着它改了代码。

## 4. 最终修复

### (a) `match.run_match` 加预算 + 加可见性

- 新增 `budget_sec`：循环内每行检查，到点停下；
- **开头就打印本次代价**：`本次代价 = N 个市场 x M 条赛程 = 最多 X 次比较`
  —— 让成本从第一秒起就是可见的；
- 每 1000 个市场打一行进度（再也不会出现十几分钟静默）；
- 截断时写一条 `runs(kind='match')` 落库，而不是只在日志里说一句。

### (b) `refodds.fetch_all` 加预算

同样新增 `budget_sec`，截断时写 `runs(kind='refodds')`。
这里有个坑值得记一笔：我最初是往 `scan.FETCH_COVERAGE_ISSUES` 这个内存列表里追加，
但那时的 `runs.note` **在扫描结束时就写完了**，追加等于写进虚空。**必须落库。**

### (c) 单步预算上限 `REFODDS_MAX_SEC = 420`

整轮 1560s 的分配写进了 `config.py`：

| 步骤 | 预算 | 说明 |
| --- | --- | --- |
| 结算 | ~20s | 第一步，很快，不设上限 |
| 扫描 | 646s | 抓取另受 `FETCH_TIME_BUDGET_SEC=720` 约束 |
| 参照价 + 匹配 | 420s | **增强项，可以少做**，所以第一个被牺牲 |
| AI 预测 | 120s | 25 次调用 |
| 报告 + 看门狗 | 8s（实测） | 保留额 180s = 20 倍余量，永不被吃 |

合计约 1214s，相对 1800s 有 ~586s 余量。
原则：**留痕优先于做多** —— 宁可少抓一点，也不能被杀得没有回执。

## 5. 一个被更正的错误结论

我在 (c) 之前一度把 `RUN_BUDGET_SEC` 从 1560 下调到 1440，
理由是"实测看到约 4 分钟的启动偏移"（任务 10:36:45 触发，
而日志里反推 `main()` 在 10:40 之后）。

**这个结论是错的。** 11:06 那次运行的日志开头写得清楚：

```
计划任务 10:36:37 触发
polytrade run @ 2026-10-14 10:36:39      ← 启动偏移只有约 2 秒
```

我当时读到的是一份**缓冲过、还没落盘完整**的 `cron.log`，就据它下了结论。
预算已改回 1560，并把这个更正写进了 `config.py` 的注释里
（留错误结论比不留更危险）。
